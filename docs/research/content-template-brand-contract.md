# Content, template and brand contract

Date: 2026-08-26

## Decyzja modelowa

Codzienny request nie powinien być instrukcją rysowania strony. LLM przekazuje
treść semantyczną, a template i brand dostarczają kompozycję. Planner wiąże
strumienie treści z portami zadeklarowanymi przez layouty kolejnych stron.

Obrazy w zwykłym Markdownzie są blokami. Strukturalny obraz może opcjonalnie
deklarować `wrap: left` albo `wrap: right`; w legacy jest to preferencja
opływania prostokątnego assetu razem z captionem. Gdy pozostały interwał tekstu
jest zbyt wąski, obraz zostaje bezpiecznie potraktowany jako zwykły blok.
`wrap` nie zmienia bitmapy i nie oznacza clippingu.

Najczęstszy payload może ograniczać się do `main`. `header`, `footer`,
`sidebar` i `quote` są opcjonalnymi override'ami, używanymi tylko wtedy, gdy
autor rzeczywiście chce zmienić domyślną zawartość szablonu.

```yaml
document:
  id: article-123
  title: A practical story

flows:
  main:
    blocks: [...]
  # optional; the template or brand may provide a default sidebar
  sidebar:
    blocks: [...]
  # optional; usually generated by the template
  footer:
    blocks: [...]

assets:
  - id: cover-photo
    role: editorial-hero
    source: root://assets/cover.png
    alt: A city seen from above
```

LLM może powiedzieć „ten materiał ma sidebar z checklistą” albo „użyj
graficznego nagłówka marki”, ale nie powinien codziennie określać `x`, `y`,
`szerokości` i zagnieżdżonych boxów.

## Własność odpowiedzialności

### LLM / agent generujący dokument

Agent odpowiada za:

- strukturę semantyczną: tytuł, sekcje, akapity, listy, cytaty;
- przypisanie treści do nazwanych flow, gdy nie wynika ono z domyślnego
  kontraktu;
- semantyczne role grafik, relacje z tekstem i tekst alternatywny;
- opcjonalne preferencje redakcyjne, np. „ten cytat jest ważny”;
- świadome override'y zawartości headera, stopki albo sidebara.

Agent nie odpowiada za:

- współrzędne, rozmiary i kolejność boxów;
- ręczne dzielenie tekstu na strony;
- budowanie logo z kilku grafik i napisów;
- decyzję, czy flow ma kontynuować się na kolejnym layoucie;
- naprawianie overflow przez ściskanie tekstu bez zgody polityki.

### Autor template'u

Template definiuje:

- dostępne layouty stron i regułę ich wyboru;
- nazwane sloty oraz flow, które mogą przyjmować;
- kolejność regionów dla każdego flow;
- boxy statyczne, blokowe i floatujące;
- powtarzalność, zmienne strony i domyślną zawartość;
- dozwolone zagnieżdżenia boxów;
- politykę braku miejsca: przesunięcie, kontynuacja, ostrzeżenie albo reject;
- alternatywne layouty, jeżeli pierwszy wariant nie spełnia ograniczeń.

Przykładowy template może deklarować:

```yaml
layouts:
  title:
    slots:
      - { id: title, kind: box, content: document.title }
      - { id: hero, kind: graphic, content: brand.hero }

  opening:
    slots:
      - { id: intro, kind: box, span: [lead, secondary] }
      - { id: lead, kind: text, flow: main, order: 1 }
      - { id: secondary, kind: text, flow: main, order: 2 }
      - { id: sidebar, kind: text, flow: sidebar, order: 1 }

  continuation:
    slots:
      - { id: column-1, kind: text, flow: main, order: 1 }
      - { id: column-2, kind: text, flow: main, order: 2 }
      - { id: column-3, kind: text, flow: main, order: 3 }

flows:
  main: { continuation: allowed, on_exhaustion: continue }
  sidebar: { continuation: unavailable, on_exhaustion: warn }
```

`main` może więc przejść z `lead` i `secondary` do trzech kolumn layoutu
`continuation`. `sidebar` ma port tylko w `opening`; nadmiar treści nie trafia
przypadkiem do artykułu.

W obecnym kontrakcie page-template ten sam wybór jest zapisany bezpośrednio w
flowie: `slots` są portami układu otwierającego, a opcjonalne
`continuation_slots` portami po przejściu na kolejną stronę. Brak
`continuation_slots` oznacza świadome odziedziczenie `slots`, a nie swobodne
szukanie dowolnego wolnego boxa. Dzięki temu np. `main` może mieć na pierwszej
stronie `[intro, metric-1, chart, narrative-body]`, a na kolejnych tylko
`[content]`, podczas gdy flow `sidebar` pozostaje wyłącznie w swoim slocie.

### Autor brandu

Brand definiuje rzeczy wielokrotnego użytku:

- fonty, style tekstowe, kolory i spacing tokens;
- logo, zdjęcia, ilustracje i ich warianty;
- graphic components, np. logo + nazwa produktu + linia opisowa;
- domyślne zawartości lub zmienne dla slotów brandowych;
- reguły użycia assetów, kontrast, minimalny rozmiar i tekst alternatywny.

Brand nie powinien definiować treści artykułu ani wymuszać, że każda strona ma
header, footer albo sidebar. Może dostarczyć komponent używany przez template,
ale to template decyduje, w którym layoucie komponent występuje.

## Zawartość specjalnych slotów

Nie każdy slot musi być zasilany przez LLM. Źródło zawartości powinno być
jawne:

```text
brand      brandowy komponent lub asset
template   stała treść i reguły template'u
document   treść dostarczona przez autora/LLM
generated  zmienna silnika, np. page.number
empty      slot celowo pusty
```

Przykłady:

- powtarzany header: `brand` + `generated(section.title)`;
- numer strony w stopce: `generated(page.number)`;
- sidebar z checklistą: `document.sidebar` albo domyślny `template`;
- graficzny header: `brand.graphicComponent('editorial-header')`;
- śródstopka: zwykły box template'u, potencjalnie spanujący regiony strony;
- logo z tekstem: jeden brandowy graphic component, nie ręcznie zagnieżdżane
  boxy w payloadzie LLM.

Ważne rozróżnienie: brand dostarcza zawartość komponentu, ale jego położenie
na konkretnej stronie nadal jest boxem zadeklarowanym przez template. Logo,
nazwa, data lub linia nagłówka nie muszą więc być osobnymi instrukcjami LLM;
mogą wypełniać jeden `lockup` albo kilka zwykłych boxów chrome. Header i
footer nie są uprzywilejowanym kanałem treści — mogą być stałe, generowane,
puste albo płynąć jak każdy inny box, zależnie od deklaracji template'u.

## Reguła fallbacku

Jeśli payload nie podaje opcjonalnego flow, template korzysta z wartości
domyślnej brandu lub template'u. Jeśli payload podaje flow, którego aktualny
layout nie przyjmuje, planner nie powinien go ignorować:

1. szuka kompatybilnego slotu w następnym dozwolonym layoucie;
2. jeżeli go nie ma, zostawia residual content;
3. zwraca ostrzeżenie albo odrzuca plan według polityki flow.

## Raport dla klienta/MCP

Wynik generowania powinien rozdzielać artefakt od jakości spełnienia wymagań:

```yaml
result:
  status: accepted-with-warnings
  artifact: { format: pdf, pages: 3 }
  decisions:
    - main continued from opening.secondary to continuation.column-1
  warnings:
    - flow: sidebar
      code: NO_COMPATIBLE_SLOT
      residual: 14 lines
      message: Sidebar content exceeded its only declared slot.
```

Klient może wtedy dostać PDF wraz z konkretną informacją, że np. sidebar nie
zmieścił się w jedynym przeznaczonym dla niego regionie, zamiast dowiedzieć się
tylko, że „renderowanie się udało”.

## Zasada projektowa

Template i brand są deklaratywnymi produktami tworzonymi wcześniej przez
człowieka. LLM jest użytkownikiem ich interfejsu, nie ich współrzędnościowym
operatorem. Jeżeli często powtarza się potrzeba ręcznego wskazywania boxów,
oznacza to zwykle brakujący slot, flow albo graphic component w template'cie.

## Stan względem prototypu

Obecny spike ma już nazwane strumienie artykułu i sidebara oraz generyczne boxy
block/float, ale ich konfiguracja nadal jest częściowo zaszyta w fixture'ach.
Kolejny krok implementacyjny to przenieść definicję layoutów i portów do
renderer-neutralnego kontraktu `PageLayout`/`FlowRoute`, a następnie zasilić go
tym samym payloadem w MCP, CLI i test harnessie.
