# Repository instructions

- Keep layout, typography, spacing, geometry, thresholds, and other tunable numeric values in the relevant YAML render configuration (`server/templates/render-config.yml`), not hardcoded in TypeScript or JavaScript. Code must read those values through the existing configuration seam. This includes visual-QA bounds and thresholds.
- Do not duplicate a configuration value as a literal in a script or renderer. If a value is needed by a tool outside the bundled renderer, load the same YAML configuration rather than copying the number.
- For visual QA round-trips, use a system LibreOffice when available; otherwise support the repository's Docker or Flatpak LibreOffice fallback instead of treating the converter as unavailable.
- The integration tests (`npm test` and `npm run test:brand`) start the MCP and CLI bundles as child processes and communicate over stdio. Run them in an environment that permits child-process creation; when the agent sandbox blocks it, use the appropriate elevated execution mode or a normal host/CI runner. Treat `spawnSync ... EPERM`, empty brand-test output, and MCP initialization timeouts as environment failures until the tests have been rerun with child-process permissions.
- Product diagnostics must be self-contained. Users must not have to write or run ad-hoc debug scripts to understand why a plan is illegal, unattractive, or incomplete. Normal CLI/MCP/report outputs should expose the relevant geometry, violations, evidence, and remediation suggestions; temporary scripts are internal verification tools only.
- Repository documentation must be written in English. Keep code identifiers, public contract names, file paths, and quoted external text unchanged; when updating an existing document, translate the prose in the touched section instead of adding new Polish text.
- Contract fields must not mix unrelated value shapes. Do not model a field as a union of primitives and structured objects (for example, `number | string | object`) merely to make a report extensible; separate numeric metrics, categorical labels, textual explanations, and geometric evidence into distinct fields.
- Prefer explicit, narrow value domains at contract boundaries. `unknown` is not a default escape hatch for domain data; use a named type or a constrained record when extensibility is required, and keep any remaining generic field deliberately scoped to an existing compatibility boundary.
- Extensible keyed data must still have an observable contract. Document and test the required keys for each consumer, omit facts that cannot be measured, and never substitute sentinel values such as `0` for unavailable measurements. Keep legality, candidate selection, and renderer geometry strongly typed even when diagnostic or scoring facts are extensible.
- For observational, diagnostic, and scoring data, prefer a fluid record with optional named properties over a rigid object that requires every possible field. Producers may emit only the facts they know, while consumers and tests declare the keys they require; do not impose a fixed structure merely for symmetry or future-proofing. This flexibility must not replace strong contracts for input, legality, geometry, or candidate selection.
- Contract tests for fluid records must assert the specific keys and value domains needed by each consumer, not require every producer to materialize one universal object shape. Missing facts remain absent (and must be handled explicitly), rather than being filled with fabricated defaults.
- Decompose functions by responsibility and ownership, not by line count. Do not introduce micro-functions only to shorten a file; a helper should represent a meaningful operation such as page, slot, cursor, geometry, calculation, mutation, or decision recording.
- Function names must expose their behavior and result. Distinguish predicates, calculations, mutations, and recording operations in the name; avoid vague names that conceal a boolean result or combine multiple responsibilities.
- Construct decisions and diagnostics through their central recorder. Planner branches pass the available domain context and a reason; they must not repeatedly construct synthetic decision objects or make debugging records the source of legality.
- Do not invent parallel domain vocabulary or abstractions. Search existing contracts and documentation before introducing a class, entity, module, or synonym; add a new concept only when it has a distinct responsibility and an identified owner.
- Test the cheapest artifact that proves the behavior. Prefer plan, legality, and placement assertions; reserve full rendering for renderer or visual-composition behavior, keep a small representative visual corpus, and merge suites that prove the same invariant.
- Do not declare a task complete without evidence for each requirement: report the checks run, generated artifacts, confirmed behavior, environment failures, and unresolved questions separately.
